01MaxisIn production since 2026

NL2SQL agent for telecom KPIs

Business teams ask BigQuery questions in plain language. A grounding guardrail validates every figure against live results before the answer is shown, or the agent abstains.

Problem

Business and finance teams could not query BigQuery themselves. Every KPI question became a ticket, and analysts spent their weeks answering them.

Decision

Treat hallucinated numbers as the failure that matters. Split the work across specialist agents, constrain SQL generation to the schema that exists (M-Schema), and put a verification step between the model and the user, with permission to say "I can't answer that".

Trace a request

Scenario

  1. "How did prepaid activations move month on month in the northern region?"

    "What was churn for the loyalty tier we launched last week?"

  2. Classified as a KPI trend question. Routed to the KPI specialist agent with the conversation so far.

    Also a KPI question on the surface. Routed the same way. The router is not where this one gets caught.

  3. Plans the query against the schema it was given: only tables and columns that exist. Generates SQL and runs it.

    No table or column in M-Schema describes a tier launched last week. The agent cannot invent one, so its confidence in the draft SQL is low.

  4. Every figure in the draft answer is checked against the live query result. They match. The answer is cleared.

    Low confidence plus figures that cannot be grounded. The guardrail blocks the answer instead of letting a plausible number through.

  5. Narrative, chart and table, with only validated figures. Anomalies are flagged where the numbers move unexpectedly.

    The user is told what could not be answered and why, and what data would be needed. No guess, no number.

  • 300+monthly users across business and finance
  • 2.4 xgrowth in questions answered, in one quarter
  • 4,000+verified answers served
  • <0.5%unverified-output rate

Live at Maxis, answering telecom KPI questions for non-technical users and growing by word of mouth. I own the LLMOps loop end to end: containerised Cloud Run deploys, versioned prompts and agent configs, reliability and cost monitoring.

Engineering notes
  • Orchestration. Google ADK on Vertex AI Agent Engine. A semantic router dispatches to specialist agents; each specialist owns one class of question.
  • SQL generation. M-Schema-aware: the agent sees a compact, typed description of the tables it may use, which removes the most common hallucination (querying a table that does not exist).
  • Grounding. The draft answer's figures are validated against the live BigQuery result set before rendering. A mismatch or a low-confidence plan triggers abstention with an explanation.
  • Conversation. Multi-turn memory and query planning, so follow-ups ("same thing for postpaid") resolve against the previous question.
  • Output. Structured narrative, chart and table for executive use, with anomaly detection on the returned series.
  • Operations. Containerised Cloud Run deployment, versioned prompts and agent configs, production reliability and cost monitoring.

02MaxisNL-to-DAX agent for Power BI

The harness that attacks the agent

A green test suite proves an agent can pass its own tests. The harness feeds it inputs the tests never covered and turns every failure into a permanent regression case.

Problem

An agent can pass every automated test and still fail real users. Happy-path suites reward memorising the demo.

Decision

Treat evaluation as an adversary, not a checklist. Build a second system whose only job is to break the first, and make each break permanent.

Trace a test run

Scenario

  1. "Total revenue by product line for last quarter." A question shaped exactly like the examples it was built on.

    A question the oracle never covered: an ambiguous time range, a measure that exists under two names, a filter phrased as a negation.

  2. All green. The generated DAX matches the expected measure and filter. This is where most evaluation stops.

    Still all green. The suite does not contain this input, so it has nothing to say about it.

  3. Not reached. A happy-path run ends at the suite, which is the problem.

    The probe scores the answer independently. The DAX filtered the wrong measure and silently returned a number. Failure recorded.

  4. Nothing new is learned.

    The failing input, the wrong output and the expected behaviour are stored as a test. From now on the suite covers it.

  5. Ships with the same blind spot it had before. Green, and no safer.

    Fixed against this class of input, and the fix cannot quietly regress. The same class of bug has not recurred since.

  • 23failures the green suite missed, each now a permanent regression case

This is now how I evaluate every agent I ship. A green suite is necessary. It is never sufficient.

Engineering notes
  • Agent. Natural language to DAX for Power BI semantic models: measure resolution, filter construction, time intelligence.
  • Probes. Generated from the classes of input the oracle did not contain: ambiguous ranges, synonyms for measures, negated filters, questions that should be refused.
  • Scoring. Each answer is scored independently of the suite, so a probe can fail an output the suite would have called correct.
  • Loop. Every surfaced failure is written back as a regression case. The suite only grows; nothing is deleted when it goes green.

03Independent build

Job Agent, a pipeline that cannot lie about you

Most LLM résumé tools happily invent experience. Here every generated claim must cite a stored fact, and anything unsourced is rejected before it can be rendered.

Problem

An agent that writes about you has to be incapable of lying. "Usually accurate" is not a property you can put on a job application.

Decision

Make citation a hard gate, not a prompt instruction. Generation may only draw on facts in a knowledge base, and a separate verification pass rejects any claim it cannot trace to one.

Trace a claim

Scenario

  1. Airflow picks up a new posting. It asks for production LLM experience on Google Cloud.

    Same posting. It also asks for Kubernetes.

  2. Requirements are extracted and matched against the knowledge base. Production LLM work on Google Cloud: strong match, several facts.

    Kubernetes: no fact in the knowledge base. The gap is recorded, not papered over.

  3. Drafts a bullet about the NL2SQL agent on Vertex AI and attaches the fact IDs it drew on.

    The model drafts "deployed services on Kubernetes" anyway. Models do this. That is why the next stage exists.

  4. Each cited fact is fetched and compared with the claim. The bullet is supported. Cleared for rendering.

    No citation resolves to a fact about Kubernetes. The claim is rejected and never reaches the document.

  5. The verified bullets are rendered with a deterministic template. Playwright assists with the application form.

    The document renders without the Kubernetes line. The gap stays visible to me, so I can decide what to do about it honestly.

  • 190+test files behind the pipeline
  • 6 xfaster tailored-application drafting
  • 0fabricated claims shipped since the gate landed

From roughly three hours per tailored application to under thirty minutes, with every claim traceable to a stored fact.

Engineering notes
  • Knowledge base. Facts about my experience live in Supabase with stable IDs. Generation prompts receive facts, not free text about me.
  • Verification. A separate pass resolves every citation and compares the claim to the fact. Unresolvable or contradicted claims are rejected; the draft is regenerated without them.
  • Rendering. Deterministic templates to PDF and DOCX, so a verified draft cannot change on the way out.
  • Orchestration. Airflow for scheduled job discovery, Playwright for assisted autofill, ~190 test files across the pipeline.

04MaxisAgent Engine

Agents that remember what they learned

Agent Engine sessions are stateless, so anything an agent learns dies with the conversation. The naive fix adds a database read to every turn.

Decision

Separate learned policy from conversational memory. Policy lives in Firestore, cached in memory and updated through realtime listeners, so every agent picks up cross-user updates instantly without a per-turn read. What one conversation teaches, every future conversation knows.

policy storeFirestore, cross-user, cached, realtime listeners
session memoryper-user, stateless sessions
agent turnreads both at zero added latency, writes learned policy back
  • 31%repeat-question deflection, quarter over quarter
  • 0 msadded per-turn latency
  • secondsto propagate a policy change, previously a redeploy
